# MemoryGraph 改进策略：解决数据源结构化的核心矛盾

> 基于《记忆图谱(1).md》的分析，针对"高价值运行时数据 vs 低确定性提取"的核心矛盾，给出具体可落地的改进方案。

---

## 策略一：伴生结构化输出（替换 AI 事后提取）

### 现状问题

数据源 4（AI 对话内容）的方案是：AI 生成纯文本回复 → 存入 step_memory → 异步 EntityExtractor 从文本中逆向提取实体。这是一条**有损路径**——信息在生成时已经存在于 LLM 的内部表示中，但写入文本后再读回来猜，精度和召回率都受限于提取 prompt 的质量。

### 改进方案

修改 `InputDialogueTask` 的 LLM 调用，要求 response **同时输出**两段内容：

```
当前:  replyText (String)
改进:  {
         replyText: String,        // 给玩家看的对话
         graphDelta: {             // 本次回复涉及的图变更
           entities: [
             { name: "苏格拉", type: "CHARACTER", confidence: 0.95, isNew: false },
             { name: "密信", type: "ITEM", confidence: 0.85, isNew: true }
           ],
           relations: [
             { from: "苏格拉", relation: "MENTIONS", to: "密信" },
             { from: "苏格拉", relation: "HAS_STATE", to: "怀疑", delta: +10 }
           ],
           stateChanges: [
             { character: "苏格拉", state: "信任", delta: -5 }
           ]
         }
       }
```

### 具体改动点

| 层 | 改动 |
|---|---|
| **Prompt 模板** | 在 `InputDialogueTask` 的 system prompt 中增加 instrucion，要求输出 JSON 格式的 graphDelta |
| **Response 解析** | 新增 `AiResponseWithGraph` 类，包含 `replyText` + `graphDelta`；修改现有解析逻辑兼容两种格式 |
| **写入路径** | 不再需要独立 EntityExtractor LLM 调用，graphDelta 直接走 GraphStore.upsertNode/Edge |
| **降级策略** | 如果 LLM 不支持结构化输出/输出格式错误，fallback 回现有纯文本 + 异步提取 |

### 收益

- **消除一次额外 AI 调用**（实体提取不再需要独立 LLM 调用，省 1 次/轮）
- **提取精度从「事后猜」变成「生成时声明」**，准确率预期从 ~70% 提升到 ~95%
- **graphDelta 天然就是增量变更**，不需要做全文比对来发现"这次新增了什么"

### 风险

- 需要修改 prompt，可能影响回复质量（通过明确的 JSON schema + few-shot 控制）
- 部分 LLM 对 JSON 约束输出的支持程度不同（gpt-4/claude 支持较好，小模型可能不稳定）

## 策略二：名称映射表替代单线程归一化

### 现状问题

文档 4.2 节的归一化管线是**有状态的单路径决策**：

```
输入名称 → trim → 全角转半角 → 去称谓后缀 → 匹配已有角色？→ 是/否
```

问题在于：
1. 称谓后缀列表（大人/小姐/阁下）硬编码，维护成本高
2. 临时 NPC/玩家的自创昵称没有入口进入系统
3. "权威来源覆盖"策略会丢失运行时产生的珍贵别名信息

### 改进方案

建立**名称映射表**，替代硬编码的归一化管线：

```sql
CREATE TABLE mg_name_mapping (
    id              BIGSERIAL PRIMARY KEY,
    script_id       VARCHAR(64) NOT NULL,
    mention_name    VARCHAR(255) NOT NULL,   -- 输入原文，如"苏格拉大人"
    canonical_id    VARCHAR(128) NOT NULL,   -- 归一化后的节点 ID
    source_type     VARCHAR(32) NOT NULL,    -- story_character / ai_extracted / runtime_memory
    confidence      DECIMAL(3,2) DEFAULT 1.0,
    first_seen_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    last_seen_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    seen_count      INT DEFAULT 1,
    UNIQUE (script_id, mention_name)         -- 同一剧本内一个别名只映射一个 canonical_id
);
```

### 写入流程

```
输入名称 "苏格拉大人" →
  1. 查询 mg_name_mapping WHERE mention_name = "苏格拉大人" AND script_id = ?
     → 命中：直接返回 canonical_id，递增 seen_count
     → 未命中：
       a. 查询 mg_name_mapping WHERE canonical_id 相似（Levenshtein）
       b. 查询 story_character 表模糊匹配
       c. 都用不上 → 创建新 CHARACTER 节点 + 新映射记录
  2. 新映射记录写入 mg_name_mapping，confidence 根据匹配方式赋值：
     - story_character 完全匹配 → 1.0
     - story_character 模糊匹配 → 0.9
     - 已有 canonial_id + 新别名 → 0.8
     - 全新节点 → 0.6
```

### 收益

- **别名本身就是有价值的图数据**——可以回答"玩家怎么称呼这个角色"
- **去掉硬编码归一化规则**，通过 seen_count 统计发现映射关系
- **支持临时 NPC**：即使不在编辑器中，运行时首次出现时也能创建节点
- **数据驱动迭代**：confidence < 0.7 的映射可以定期人工审核或走二次 AI 确认

### 与现有方案对比

| 维度 | 原方案（归一化管线） | 改进方案（名称映射表） |
|---|---|---|
| 新角色支持 | 硬匹配，新角色创建门槛高 | seen_count 达到阈值后自动确认 |
| 别名可追溯 | 无记录 | 完整别名历史 |
| 维护成本 | 称谓后缀列表需手动更新 | 数据自学习，seen_count 自动累计 |
| 一致性 | 每次走归一化函数，可能有逻辑漂移 | INSERT ON CONFLICT，确定性写入 |

## 策略三：分级图压缩（遗忘机制）

### 现状问题

文档提到图数据膨胀风险但未解决。按每天 100 轮对话、每轮产生 3-5 个节点计算，一个月产生 ~10,000 个运行时节点。Recursive CTE 在数万节点下的性能未验证。

### 改进方案

**三级生命周期的节点管理**，在 mg_node 增加 `lifecycle` 字段：

```sql
ALTER TABLE mg_node ADD COLUMN lifecycle VARCHAR(16) DEFAULT 'volatile';
-- volatile: 易失，可物理删除
-- compressible: 可压缩，可合并为摘要
-- persistent: 持久，保留
```

### 三个层级详细设计

| 层级 | 标记条件 | 行为 | 触发时机 |
|---|---|---|---|
| **volatile** | 创建时默认，source_type IN ('ai_extracted', 'runtime_character') | 物理删除 | 超过 N 轮对话未被任何边引用（默认 50 轮） |
| **compressible** | 连续 3+ 个节点属于同一 source 且 semantic_similarity > 0.8 | 合并为摘要节点，原节点添加 `SUPERSEDED_BY → 摘要节点` | 每日后台批处理 |
| **persistent** | 被预设节点引用 / 被 5+ 个事件引用 / scene_id 跨 3+ 场景 | 保留不动 | 不触发 |

### 压缩示例

```
压缩前：
  EVENT:发现密信          EVENT:调查密信          EVENT:交出密信
    (step 15)                (step 22)               (step 35)

压缩后：
  摘要节点: "密信相关事件链（发现→调查→交出）"
    SUPERSEDES → EVENT:发现密信
    SUPERSEDES → EVENT:调查密信
    SUPERSEDES → EVENT:交出密信
```

### CTE 查询适配

在 Recursive CTE 中加入 lifecycle 过滤：

```sql
-- volatile 节点只允许 1 hop
AND NOT (n.lifecycle = 'volatile' AND gw.depth >= 1)

-- compressible 节点允许 2 hops
AND NOT (n.lifecycle = 'compressible' AND gw.depth >= 2)
```

这样 volatile 节点只能做"直接邻居"查询，不会深入扩散。

## 策略四：查询层双视图分离

### 现状问题

mg_node 统一存储所有来源数据，但它们的生命周期和访问模式完全不同：

| 来源 | 写入频率 | 变更模式 | 查询深度需求 |
|---|---|---|---|
| 编辑器预设 | 低（保存时） | 覆盖写 | 深（3 hops） |
| 场景摘要 | 中（每场景一次） | 追加写 | 中（2-3 hops） |
| 运行时数据 | 高（每轮对话） | 快速写入，快速淘汰 | 浅（1-2 hops） |

### 改进方案

**不在表层面分离**（避免 join 开销），而是在查询层面构建**分层的 CTE**：

```sql
WITH RECURSIVE static_walk AS (
    -- 编辑器数据：允许 3 hops，不受运行时数据影响
    SELECT n.id, n.node_type, n.content, 0 AS depth
    FROM mg_node n
    WHERE n.script_id = :scriptId
      AND n.source_type IN ('story_preset_memory', 'story_scene_memory', 'story_step_memory')
      AND n.id = ANY(:seedNodeIds)

    UNION
    SELECT n.id, n.node_type, n.content, sw.depth + 1
    FROM static_walk sw
    JOIN mg_edge e ON e.from_node_id = sw.id AND e.script_id = :scriptId
    JOIN mg_node n ON n.id = e.to_node_id
    WHERE sw.depth < 3
      AND n.source_type IN ('story_preset_memory', 'story_scene_memory', 'story_step_memory')
),
dynamic_walk AS (
    -- 运行时数据：限制 1 hop，避免图爆炸
    SELECT n.id, n.node_type, n.content, 0 AS depth
    FROM mg_node n
    WHERE n.script_id = :scriptId
      AND n.source_type IN ('ai_extracted', 'runtime_character', 'character_state')
      AND n.id = ANY(:seedNodeIds)

    UNION
    SELECT n.id, n.node_type, n.content, dw.depth + 1
    FROM dynamic_walk dw
    JOIN mg_edge e ON e.from_node_id = dw.id AND e.script_id = :scriptId
    JOIN mg_node n ON n.id = e.to_node_id
    WHERE dw.depth < 1    -- 运行时数据仅 1 hop
)
SELECT * FROM static_walk
UNION
SELECT * FROM dynamic_walk
ORDER BY depth, id;
```

### 收益

- 运行时数据膨胀**不会拖慢核心剧本知识查询**
- 不增加表结构复杂度，只在查询层做隔离
- 后续可以分别缓存静态视图（TTL = 5min）和动态视图（TTL = 10s）

## 策略五：评估飞轮

### 现状问题

文档提到实体提取是不确定性的，但没有建立任何评估机制。这意味着：
1. 无法知道当前提取的质量（precision/recall）
2. 修改提取逻辑后，无法判断是变好了还是变差了
3. 无法定位具体哪类实体提取最薄弱

### 改进方案

构建一个小而闭环的评估集，核心是一个接口 + 一个 JSON 文件：

```java
// 接口定义
interface EntityExtractorEvaluator {
    EvaluationResult evaluate(List<TestCase> testCases);

    class TestCase {
        String inputText;              // AI 回复原文
        List<Entity> expectedEntities; // 期望提取的实体
        List<Relation> expectedRelations; // 期望提取的关系
    }

    class EvaluationResult {
        double entityPrecision;
        double entityRecall;
        double relationPrecision;
        double relationRecall;
        Map<String, Double> precisionByEntityType; // CHARACTER / ITEM / EVENT 分别统计
        List<FailureCase> failures; // 具体失败案例
    }
}
```

### 评估集构建

不需要大规模，重点是**覆盖边界情况**：

```
test_cases.json:
  20 个测试用例，覆盖：
  - 5 个标准对话（已有角色+已有关系）
  - 5 个包含新角色引入的对话
  - 3 个包含同义词/别名的对话（"苏格拉大人" → "苏格拉"）
  - 3 个短回复（1-2 句话，信息密度低）
  - 2 个包含实体状态变更的对话（"白浅感到一阵不安" → STATE:不安）
  - 2 个空/边界输入（"嗯"、"好的"等无信息回复）
```

### 集成到 CI

```
每次修改 EntityExtractor / graphDelta prompt 后：
  → 自动运行评估集
  → 对比 baseline 指标
  → precision/recall 下降 > 5% → CI 告警
  → 通过后更新 baseline
```

### 工作量估算

- 构建 20 个测试用例 + 人工标注：0.5 天
- 编写 EvaluationResult 接口 + 评估执行逻辑：0.5 天
- CI 集成：0.5 天
- **总计：1.5 天，Part B 的开发效率预计提升 30%+**

## 策略六：写入路径统一为 UPSERT 语义

### 现状问题

文档中不同数据源的写入策略不一致：
- 数据源 1-3：同事务写入，覆盖写
- 数据源 4：异步 + 幂等，但"幂等"没有精确定义
- 数据源 6：追加写（不覆盖，建 SUPERSEDES 链）

### 改进方案

**所有写入统一为 UPSERT + 版本号语义**，不管同步还是异步：

```sql
INSERT INTO mg_node (id, script_id, node_type, content, attributes, version, updated_at)
VALUES (:id, :scriptId, :nodeType, :content, :attributes, 1, NOW())
ON CONFLICT (id, script_id) DO UPDATE SET
    content      = CASE WHEN mg_node.version < :version THEN :content ELSE mg_node.content END,
    attributes   = CASE WHEN mg_node.version < :version THEN :attributes ELSE mg_node.attributes END,
    version      = mg_node.version + 1,
    updated_at   = NOW()
RETURNING version;
```

关键点：
- **不是「版本号大的覆盖」，而是「后写入的递增版本，保留所有历史」**
- 版本号不是时间戳，而是写入序号，避免了时钟不同步问题
- 查询时默认取最新版本，但工具/调试接口可以查历史

### 各数据源的 version 赋值

| 数据源 | version 策略 | 说明 |
|---|---|---|
| 编辑器保存 | 每保存一次 version++ | 等同每次编辑是一个版本 |
| 场景摘要 | version = 场景序号 | 场景按顺序推进，version 递增 |
| AI 对话提取 | version = step_index | 对话步骤天然单调递增 |
| 角色状态变更 | version = 变更序号 | 每条状态变更加 1 |
| 存档恢复 | version = 恢复前的最大 version + 1 | 重建的节点从新版本开始 |

### 收益

- **所有写入路径使用同一个 DAO 方法**，不存在 n 种写入策略
- **天然支持幂等**：同一条数据重复写入不会产生脏数据
- **历史可回溯**：调试时可以看到节点内容的变更轨迹（但需要额外的 version 快照表来存历史）

## 实施路线图调整建议

基于以上 6 个策略，对文档原有的路线图做调整：

### Part A 调整（图存储基础设施）

| 原步骤 | 调整 |
|---|---|
| A1-A2 创建表 | 增加 `mg_name_mapping` 表、mg_node 增加 `lifecycle` 列 |
| A3 GraphStore | UPSERT 语义替代普通 CRUD |

### Part B 调整（运行时数据写入）

| 原步骤 | 调整 | 说明 |
|---|---|---|
| B1 状态变更 | 复用 UPSERT + SUPERSEDES | 与策略六一致 |
| B2 runtimeMemory | 写入时同步写入 mg_name_mapping | 别名策略 |
| B3-B4 实体提取 | **改为策略一的伴生结构化输出** | 省去独立的 EntityExtractor LLM 调用 |
| B5 归一化管线 | **改为策略二的名称映射表** | 去掉硬编码 |
| B6 异步执行 | 伴生输出后同步写入 | 不再需要独立异步路径 |

### Part C 调整（存档一致性）

| 原步骤 | 调整 |
|---|---|
| C1-C3 | 生命周期按 lifecycle 列过滤，不再依赖 source_type 字符串匹配 |

### 新增步骤

| 步骤 | 内容 | 工作量 |
|---|---|---|
| S1 | 名称映射表 `mg_name_mapping` DDL + 读写逻辑 | 1d |
| S2 | 伴生结构化输出 prompt + response 解析 | 2d |
| S3 | 分级压缩后台批处理 job | 2d |
| S4 | 评估集 + 评估框架 | 1.5d |
| S5 | 查询层双视图 CTE 重构 | 1d |

### 调整后总工作量

| 部分 | 原预估 | 调整后 | 差 |
|---|---|---|---|
| Part A | 8d | 8d | — |
| Part B | 8d | 6d | -2d（省去独立 EntityExtractor 和归一化管线） |
| Part C | 4d | 3d | -1d（lifecycle 替代 source_type 字符串匹配） |
| 新增 S1-S5 | — | 7.5d | +7.5d |
| **合计** | **20d** | **24.5d** | +4.5d |

多出的 4.5 天换来的能力：
- 实体提取不再需要独立 LLM 调用（长期省成本）
- 名称映射自学习，不需要人工维护硬编码规则
- 图压缩防止数据无限膨胀
- 评估飞轮确保迭代质量可度量
- 查询效率不随数据量增长而衰减
